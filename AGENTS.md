# Capy Print — руководство для агентов

Инструкции распространяются на весь репозиторий. Перед изменениями прочитайте этот файл, проверьте состояние Git и изучите затрагиваемый сценарий целиком.

## Назначение проекта

Capy Print — приложение копицентра для заказа печати документов и фотографий. Клиент загружает файлы, выбирает бумагу, цветность, количество копий, двустороннюю печать и срок выполнения. Сотрудник управляет заказами и статусами; клиент получает сообщение о готовности.

Сейчас реализована интеграция с Telegram Mini Apps. Приоритет развития — запуск того же приложения во VK Mini Apps с сообщениями от сообщества VK, затем обновление UI/UX. План и критерии приёмки: [docs/vk-mini-apps-ui-ux/README.md](docs/vk-mini-apps-ui-ux/README.md).

Оплата при получении описана в текущем FAQ бота. Онлайн-оплата, расчёт стоимости, VK, промокоды и реферальная программа пока не реализованы. Не описывайте запланированные функции как доступные пользователю.

## Стек

- Next.js 16, App Router, React 19, TypeScript 7 со strict-режимом; API TypeScript 6 через npm alias для ESLint и других инструментов.
- Mantine 9 и Tailwind CSS 4 для интерфейса; Lucide 1 для иконок. `config/theme.ts` сохраняет прежние цвета light через `v8CssVariablesResolver`.
- React Hook Form и Zod для клиентских форм.
- TanStack Query и Axios для клиентских запросов.
- PostgreSQL, Prisma и PostgreSQL adapter закреплены на 7.10.0 без диапазона версий.
- AWS SDK S3 Client для загрузки файлов в Timeweb; настройки только серверные в env.
- `@tma.js/sdk-react` для Telegram Mini Apps.
- Telegram Bot API вызывается через Axios; наличие `grammy` в зависимостях не означает, что webhook построен на нём.

Запросы используют Prisma и транзакции Serializable с максимум тремя попытками при P2034; raw SQL в API не используется. Уведомления отправляются только после успешного commit, вне повторяемой операции.

Нужна миграция `20261011020000_order_cancellation_reason`; агент к реальной базе её не применял. При возврате отменённого заказа в другой статус причина очищается. На главной ADMIN не видит предложения скидок; сотрудники получают уведомление только о новом заказе, без дополнительного сообщения при завершении.

## Правила изменения кода

- Сначала проверьте `git status`. Сохраняйте несвязанные изменения пользователя; не откатывайте их ради задачи.
- Держите изменения в пределах запроса. Не смешивайте интеграцию VK с массовым редизайном.
- Сохраняйте существующее поведение Telegram при введении платформенных адаптеров.
- Используйте TypeScript, существующие компоненты и стиль соседних файлов. Новую зависимость добавляйте, когда она решает конкретную задачу.
- Используйте стрелочные функции через `const`, включая экспорты; где возможно — неявный возврат выражения или `(...)`. Не используйте IIFE. После изменений прогоняйте затронутые файлы через Prettier.
- SDK платформ, DOM и browser storage используйте только на клиенте. Секреты, проверка подписей, Prisma и отправка сообщений остаются на сервере.
- Проверяйте входные данные и права на сервере. Клиентская Zod-схема и скрытая кнопка не заменяют серверную проверку.
- Пользователь для создания и чтения заказов должен определяться проверенной авторизацией. Переданный клиентом ID не является подтверждением личности.
- Для доступа к заказу проверяйте владельца или роль ADMIN. Не предоставляйте клиенту общий административный список.
- Идентификаторы внешних платформ не смешивайте с внутренним `User.id`. Не объединяйте аккаунты по имени, username или совпадению числового ID.
- Учитывайте BigInt при ответах API: используйте согласованную сериализацию и JSON-типы, а не прямой JSON.stringify модели Prisma.
- Изменения БД оформляйте миграциями с сохранением данных. Не переписывайте применённые миграции и не используйте reset/db:push как способ выпуска изменений в production.
- Перед выполнением команды, меняющей БД, выясните целевое окружение. Не запускайте миграции на неизвестной или production-базе как часть обычной проверки.
- Обновляйте env-документацию, карту проекта и план, если меняется архитектура или статус задачи.
- Не публикуйте приложение, не отправляйте реальные тестовые сообщения и не меняйте настройки внешних сервисов без соответствующего поручения.

## Известные ограничения текущей реализации

Это задачи для исправления, а не образцы архитектуры:

- Для сессий нужны миграции `20261003000000_mini_app_sessions` и `20261003010000_persistent_sessions`; к текущей базе они пока не применены. Bearer с префиксом vk_/telegram_ хранится только в памяти и действует до отзыва. После reload без query VK восстанавливает launch params через Bridge в iframe/WebView; старые или недоступные параметры требуют повторного открытия Mini App. Автоматические запросы запуска имеют таймаут 10 секунд, окно согласия не ограничено. Нативные VK/Telegram клиенты ещё не проверены.
- Telegram webhook не проверяет secret token. POST /api/uploads требует серверную сессию и проверяет MIME и размер. Для постоянных ссылок требуется публичное чтение объектов S3, а лимит тела запроса на хостинге — минимум 16 МБ плюс 64 КБ; реальный бакет пока не проверен.
- `User.telegramId` остаётся nullable переходным полем Telegram-уведомлений; аккаунты Telegram/VK разделены через UserIdentity. VK Bridge получает профиль во время загрузки приложения, PATCH сохраняет его в существующий User, затем скрывается лоадер. Темы/платформенные действия ещё не реализованы. Запрос разрешения и отправка сообщений сообщества реализованы; внешние настройки и нативная проверка VK ещё нужны.
- Общий сервис клиентских сообщений вызывается после изменения заказа; ошибка отправки не сохраняется для повторения. Нет журнала доставки и очереди; сбой после сохранения статуса может потерять уведомление.
- Для однократного диалога сообщений нужна миграция `20261009000000_vk_messages_preference`, к текущей базе не применена. `UserIdentity.vkMessagesEnabled`: null — выбор не сделан, true — согласие, false — отказ; перед отправкой дополнительно проверяется разрешение VK.
- Расписание в боте и форме расходится. При унификации требуется подтвердить реальные часы копицентра.
- `deadlineAt` хранится как String; POST/PATCH проверяют дату и сохраняют строку.
- Для скидки на каждый третий выполненный заказ нужна миграция `20261011010000_completed_order_loyalty`. Она сохраняет заказы, переводит PROCESSING в PRINTING, заполняет User.completedOrdersCount по существующим COMPLETED и переносит уже назначенные 15% в Order.discountPercent. К реальной базе агент её не применял. COMPLETED окончательный: сервер отклоняет возврат в работу/отмену, комментарий редактируется. Счётчик увеличивается ровно один раз при завершении в транзакции Prisma Serializable и сохраняется при удалении заказа. Процент 5 и интервал 3 — в config/loyalty.ts; скидки не складываются. Прогресс — в components/loyalty-progress.tsx, общий блок — components/order-offers.tsx, сохранённая скидка — components/order-discount-banner.tsx, чистые правила — lib/order-discounts.ts, серверный helper — lib/order-discounts.server.ts. Сотрудник применяет сохранённый процент при оплате, автоматического расчёта стоимости нет.
- Для скидки 15% на первый заказ нужна миграция `20261011000000_first_order_discount`, к текущей базе не применена. GET пользователя возвращает `isFirstOrder`, если нет никаких заказов (включая отменённые). POST определяет и сохраняет `Order.isFirstOrder` в транзакции Prisma Serializable; старые заказы получают false. Сотрудник применяет скидку при оплате, автоматического расчёта стоимости нет. При удалении всех заказов пользователь снова считается новым; Telegram/VK аккаунты пока независимы.

## UI/UX

Safe area задаётся общими CSS-переменными в `app/globals.css` и применяется в `PageContainer`, диалогах Mantine, Lightbox и toast. `lib/mini-app/vk-safe-area.ts` подписывается на `VKWebAppUpdateConfig`/`VKWebAppUpdateInsets` до `VKWebAppInit`, получает начальные insets через `VKWebAppGetConfig`, снимает подписку при размонтировании. Для нативного VK (`bridge.isWebView()`) сверху дополнительно резервируется 56 px под плавающее меню; при отсутствии данных Bridge используются fallback 24 px сверху и 16 px снизу. Системные CSS env и VK insets объединяются через max, а не складываются. `viewportFit: cover` включён в корневом layout. Новые страницы должны использовать общий контейнер, без собственного повторного safe-area padding. Нативная повторная проверка iOS/Android после изменения остаётся необходимой.

- Пользовательские тексты — на русском. Сохраняйте узнаваемость капибары и зелёной палитры.
- Основной сценарий — телефон в WebView Telegram/VK. Проверяйте маленький экран, клавиатуру, safe areas, темы и кнопку назад.
- Показывайте состояния загрузки, ошибку с понятным восстановлением, пустой список и успешное завершение.
- Не показывайте фиктивные цены, сроки, скидки, гарантии удаления файлов или автоматические проверки, которых ещё нет.
- Анимации короткие, не мешают работе с формой, учитывают `prefers-reduced-motion`. Не анимируйте каждый элемент и не добавляйте библиотеку только ради hover.
- Используйте корректные label, доступный контраст и управление с клавиатуры. При переходах между шагами сохраняйте введённые данные.

## Проверка и завершение задачи

После изменений кода выполняйте проверки соразмерно задаче: TypeScript, ESLint затронутых файлов, build при изменении интеграции/сборки. Не добавляйте бессодержательные тесты на документацию или косметические изменения.

Для авторизации, миграций и уведомлений нужны проверки поведения: неверная/просроченная подпись, чужой заказ, сохранение существующих данных, отказ в сообщениях, ошибка доставки, отсутствие дублей. `npm test` проверяет launch data и HTTP-контракт авторизации; остальные сценарии добавляйте при реализации соответствующих этапов. Выбранный способ проверки документируйте.

Для интерфейса проверьте затронутый сценарий в браузере; тест в обычном браузере не подтверждает работу нативного Bridge. Для платформенных изменений требуется проверка внутри Telegram/VK.

При сдаче укажите, что изменилось, что проверено и что ещё зависит от внешних настроек. Для изменений только документации достаточно проверки ссылок, путей и diff. Не коммитьте и не отправляйте изменения в remote без поручения пользователя.
