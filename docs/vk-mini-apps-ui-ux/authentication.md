# Авторизация и серверные сессии Mini Apps

## Исправления профиля и заказов — 8 октября 2026

После входа из VK клиент вызывает `VKWebAppGetUserInfo` и сохраняет имя, фамилию и фото через `PATCH /api/user` с Bearer-сессией. Сервер допускает только VK-сессию, сверяет ID профиля с `UserIdentity.externalUserId` и обновляет существующий `User.id`. Роль, идентификаторы и привязка заказов не меняются. Дополнительных секретов или миграций для этого исправления не требуется. Имена и фото — отображаемые данные из Bridge, а не подписанные доказательства личности; они не участвуют в авторизации. Подпись launch params и серверная сессия остаются единственным источником владельца и платформы. Поля произвольного профиля, роли и чужого ID отклоняются.

Профиль загружается в процессе инициализации: серверная сессия → `VKWebAppGetUserInfo` → `PATCH /api/user` → обновление пользователя клиентской сессии → скрытие лоадера. Отдельного фонового процесса синхронизации нет. Автоматические запросы запуска ограничены таймаутами, описанными ниже. При ошибке получения или сохранения профиля отображается ошибка входа с повтором; интерфейс заказов открывается после завершения загрузки. Ранее записанное имя/фото при ошибке не стирается. Уже существующие VK-пользователи получают имя при следующем успешном открытии приложения без создания нового аккаунта. В `User.telegramId` у них по-прежнему `NULL`: их VK ID хранится в `UserIdentity`.

Заказы в API включают `user.identities`. Telegram-уведомление сотрудникам и детали заказа показывают платформу, имя, ID и ссылки на профиль/переписку. Ссылки VK строятся из серверной identity, поэтому доступны даже у старого заказа с пустым именем. HTML в имени, комментарии и названиях файлов экранируется для Telegram. Для Telegram используется username-ссылка или `tg://user?id=…`. Возможность начать переписку зависит от настроек аккаунта клиента. Отправка сообщений клиентам от сообщества VK остаётся отдельной задачей.

После создания заказа клиент инвалидирует список TanStack Query. Запросы списка ждут завершения инициализации; ключи разделены по внутреннему пользователю и `scope`. «Мои заказы» явно различает пустую историю и ошибку запроса и предлагает повтор загрузки. Владелец по-прежнему берётся из Bearer-сессии; внешние ID не используются как `Order.userId`.

Проверки: автоматический сценарий с реальным Axios interceptor, QueryObserver и HTTP-обработчиками на заглушках БД — пустая история VK → создание заказа → обновлённая история того же внутреннего пользователя. Отдельно проверяются обновление профиля без изменения пользователя/заказов, чужой ID, роль/платформа, ошибка сохранения, очистка сессии во время запроса, формат уведомления и отказ Telegram API. Реальные сообщения в тестах не отправляются. В доступной локальной `capy_print_dev` у пользователя №6 на момент диагностики было 0 заказов, последний заказ в базе — №5; заказ №62 со скриншота не воспроизведён на этой базе. Проверка опубликованного окружения и нативного VK остаётся необходимой.

Метод получения профиля повторно сверён с [контрактами текущего VK Bridge](https://github.com/VKCOM/vk-bridge/blob/master/packages/core/src/types/data.ts). Репозиторий `vk-mini-apps-api` архивирован и не используется как источник актуального статуса SDK.

## Вход и транспорт

```http
POST /api/auth/session
Authorization: telegram <исходная строка initData>
```

Для VK: `Authorization: vk <query-строка launch params>`. Если полный набор параметров есть в URL, клиент передаёт `window.location.search` целиком, включая допустимый начальный `?`. После reload без параметров используется сериализованный ответ `VKWebAppGetLaunchParams`: исходные `vk_*` и `sign`. Оба пути проходят одинаковую серверную проверку. Для Telegram используется `retrieveRawInitData()` из существующего SDK, без повторной сериализации профиля/launch params. Body не используется для подтверждения личности. Секреты, проверка подписи и разрешение внутреннего пользователя остаются на сервере.

Ответ содержит `token`, `platform` и `user`: внутренний числовой `id`, текущую роль, имя/username и строковый либо null `telegramId`. Сырой токен возвращается только при создании сессии. В БД записываются SHA-256 хеш случайного 256-битного токена, identity и время создания. Сессия **без истечения по времени**, действует до явного отзыва; срок launch data для входа — **300 секунд** с допуском будущего времени **30 секунд**. Это политика Capy Print, а не лимиты VK. Повторный вход с действительными launch data допустим: пользователь/identity переиспользуются, токен каждый раз новый.

Бизнес-запросы используют:

```http
GET /api/orders?scope=mine
Authorization: Bearer vk_<случайный токен сессии>
```

Выбран один транспорт: Bearer в заголовке, токен хранится **только в памяти** клиентского модуля. Вход и бизнес-запросы используют Axios с `withCredentials: false`; cookies не устанавливаются и не принимаются как авторизация. Axios обращается к `/api/` на том же origin. UploadThing получает Bearer через функцию `headers` для запроса к нашему middleware. Никаких токенов в URL, localStorage, sessionStorage или VK storage нет.

Причина выбора: VK использует iframe и WebView, в том числе оба варианта на iOS; ограничения сторонних cookies не должны определять доступ к API. `SameSite=None; Secure` само по себе не гарантирует доступность cookies при блокировке браузером. Хранение в памяти также не требует browser storage, но токен доступен JavaScript: XSS может его украсть. Нужны обычные меры защиты от XSS и HTTPS при развёртывании.

Переходы Next.js между страницами сохраняют сессию в памяти. Повторная инициализация на той же платформе переиспользует действующий токен; параллельные вызовы входа объединяются в один запрос. Каждый фактический успешный POST входа выдаёт новый токен, но предыдущие сессии автоматически не отзывает: они действуют до DELETE с их Bearer. Префикс vk_/telegram_ позволяет определить платформу, но сервер дополнительно сверяет её с identity в БД. Сам по себе префикс не подтверждает личность. Закрытие WebView само по себе не отзывает серверную сессию.

Полная перезагрузка создаёт новую сессию, только если подписанные параметры доступны и свежие. Потеря query восстанавливается через `VKWebAppGetLaunchParams` в VK iframe/WebView. Если Bridge не возвращает параметры либо их `vk_ts` старше допустимого срока, пользователь должен заново открыть Mini App. Fallback не продлевает TTL и не хранит Bearer в storage. После отзыва бизнес-API возвращает 401, клиент показывает восстановление входа и не размонтирует уже заполненную форму. Refresh-token не нужен: сессия бессрочная. React получает изменения клиентской сессии через useSyncExternalStore, без window events. Серверный logout уже доступен, кнопка выхода в интерфейс не добавлялась. Открытые проверки: [повторная сверка](#повторная-сверка-vk--9-октября-2026).

Все ответы сессии и персональные успешные ответы API имеют `Cache-Control: no-store`. Не логировать Authorization, launch data, объекты Axios error (они содержат заголовки) или токены. HTTPS/CSP и ограничения встраивания проверяются отдельно в настройках хостинга.

## Маршруты и права

| Маршрут                           | Правило                                                                          |
| --------------------------------- | -------------------------------------------------------------------------------- |
| `POST /api/auth/session`          | Проверенная подпись, ожидаемый app ID, время; разрешает identity и выдаёт сессию |
| `GET /api/auth/session`           | Действующая сессия; текущий пользователь и платформа, без токена/хеша            |
| `DELETE /api/auth/session`        | Удаляет запись по хешу Bearer; повторный вызов возвращает 204                    |
| `POST /api/auth/verify`           | Сохраняет диагностический контракт проверки launch data; не создаёт сессию       |
| `GET /api/user`                   | Только текущий пользователь сессии; query ID игнорируется                        |
| `PATCH /api/user`                 | Обновление профиля текущего VK-пользователя; ID совпадает с identity сессии      |
| `POST /api/orders`                | Владелец из сессии; переданные telegramId/userId не участвуют в авторизации      |
| `GET /api/orders`                 | По умолчанию `scope=mine`, даже для администратора; `scope=all` только ADMIN     |
| `GET /api/orders/details?id=…`    | Владелец или ADMIN; чужой/отсутствующий заказ — 404                              |
| `PATCH /api/orders/details?id=…`  | Только ADMIN; поля и enum проверяются на сервере                                 |
| `DELETE /api/orders/details?id=…` | Только ADMIN, соответствует существующему интерфейсу сотрудника                  |
| UploadThing middleware            | Действующая сессия и допустимый MIME; metadata содержит внутренний User.id       |

`lib/auth.ts` получает сессию из БД и каждый раз читает текущую роль пользователя. `x-telegram-id`, query/body ID, cookies, возвращённый клиентом объект identity и launch data в бизнес-запросе не являются авторизацией. Клиентская Zod-проверка дополнена серверной проверкой полей заказа и параметров списка. `deadlineAt` в PATCH теперь остаётся строкой, как в схеме БД.

## Identity и миграция

`UserIdentity` хранит provider TELEGRAM/VK, строковый `externalUserId` и ссылку на внутренний User. Уникальность `(provider, externalUserId)` разделяет одинаковые числовые ID разных платформ. Роль VK admin/editor из launch params не превращает пользователя в сотрудника. Аккаунты автоматически не объединяются.

Миграция `prisma/migrations/20261003000000_mini_app_sessions/migration.sql`:

- Делает `User.telegramId` nullable, сохраняя уникальность и все существующие значения.
- Создаёт UserIdentity и переносит Telegram ID строками без потери точности.
- Сохраняет `User.id`, роли и `Order.userId`; создаёт таблицу Session и индексы.
- Связывает удаление пользователя/identity с удалением сессий.

Telegram-вход обновляет профиль только из подписанного `user` и переиспользует прежний User по telegramId. Пользователь Telegram, появившийся после backfill, также получает identity при первом входе. VK-вход создаёт отдельного User с ролью USER и nullable telegramId; профиль через Bridge ещё не реализован. `User.telegramId` остаётся переходным полем для Telegram-уведомлений; его полное удаление и сохранение канала в заказе относятся к последующим этапам.

Порядок выпуска: проверить резервную копию и целевое окружение, выполнить существующие миграции через `npm run db:migrate:deploy`, затем развернуть код с новым клиентом Prisma. Старый клиент, передающий только ID, после перехода получает 401. Смешанный rollout старого клиента/нового сервера не поддерживается. Не применять миграцию к неизвестной базе; не использовать reset/db:push. Миграция `20261003010000_persistent_sessions` удаляет expiresAt и его индекс, сохраняя остальные данные. Старые токены без префикса требуют нового входа. Seed и Docker используют только отдельную локальную capy_print_dev.

## Конфигурация и алгоритмы

Новые секреты для сессии не нужны: используется непрозрачный случайный токен и серверная таблица. `SESSION_SECRET` не требуется. Нужны существующие `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`, а для VK — `VK_APP_ID` и защищённый ключ приложения `VK_APP_SECRET`. Токен сообщества не заменяет защищённый ключ. Для клиентских API используется тот же origin; `NEXT_PUBLIC_BASE_URL` сохраняется для других существующих настроек, не выбирает адрес отправки Bearer.

Telegram: отсортированные декодированные поля через LF, HMAC-SHA256 с ключом `HMAC-SHA256(key=WebAppData, data=botToken)`. Исключается только hash; необязательная signature участвует в HMAC. VK: отсортированные `vk_*`, значения через encodeURIComponent, HMAC-SHA256 с защищённым ключом приложения, base64url без padding. После подписи проверяются app ID и vk_ts. Дубли ключей, неверные подписи и время отклоняются. Проверка подписи делегирована `@tma.js/init-data-node` и `vk-launch-params`; собственная реализация HMAC и сравнения удалена. Для VK передаются только vk_* и sign, внешний ID читается строкой. SHA-256 для сессии — стандартный node:crypto, без собственного алгоритма. ID Telegram должны быть точными безопасными целыми, VK сохраняются десятичными строками.

## Проверки и ограничения

Финальные локальные проверки 03.10.2026: **124/124 теста**, TypeScript (`npm run compile`), ESLint затронутых файлов и `npm run build` успешны. Сборка содержит `/api/auth/session`. В diff-check замечания только к пробелам в автоматически сгенерированных Prisma-файлах; вручную они не исправлялись.

`npm test`: Node test runner через tsx; синтетические секреты и заглушки Prisma для маршрутов, реальные SQL-миграции на отдельном PGlite (PostgreSQL WASM в памяти). PGlite — явная dev-зависимость, уже использовавшаяся транзитивно Prisma. Тесты не читают .env и не используют DATABASE_URL; реальные сообщения блокируются заглушкой Axios.

Покрыты подписи/TTL/подмена платформы, хеширование и работу сессии спустя 90 дней, отзыв, повторный вход без новых пользователей, текущая роль из БД, сохранение Telegram-пользователя, разделение Telegram/VK, неподписанные ID, чужие заказы, создание владельцем сессии, права ADMIN, UploadThing middleware, транспорт без cookies/storage и единственный параллельный вход клиента. SQL-проверка применяет всю историю миграций к пустой БД, создаёт старого администратора/заказ, выполняет новую миграцию и проверяет данные, уникальность identities и каскад сессий.

Локальный браузер: экран запуска вне Mini App, повтор входа и сообщение о ненастроенной авторизации VK (503) на ширине 360 px. Это не подтверждает работу Bridge, настоящего VK iframe, iOS/Android или загрузку в UploadThing. Текущая база по запросу пользователя не мигрировалась. Нужны dev-база с миграцией и настроенный HTTPS URL Mini App для полной проверки.

Матрица ручной приёмки: Telegram iOS/Android, VK desktop iframe, VK mobile web iframe, VK Android WebView, VK iOS (iframe до модерации и WebView после). Для каждого: вход с cookies запрещёнными, переходы между страницами, свои/чужие заказы, reload через пять минут, отзыв, потеря сети и повтор входа. Проверять коды ответов и наличие схемы Bearer, не сохранять значения заголовков/параметров в отчёте.

Клиент использует общий MiniAppProvider/useMiniApp и два адаптера в lib/mini-app. Провайдер выбирает адаптер по launch query либо окружению Telegram/VK; VK вызывает VKWebAppInit до получения fallback-параметров и запроса сессии. Компонент разрешения также импортирует VK Bridge, поэтому это не обещание загрузки только одного SDK во всём клиентском bundle. Пользователь и платформа берутся непосредственно из store/api/session, роль — из user.role; контекст не хранит их повторно. Подписка на очистку сессии скрывает интерфейс, сохраняя смонтированную форму для повторного входа.

На этапе перехода на общий провайдер прошли 127/127 тестов, TypeScript, ESLint затронутых файлов и production-сборка Next.js без повторной генерации Prisma. В локальном браузере проверен экран ошибки запуска вне Mini App. Проверки адаптеров: выбор Telegram/VK, отказ вне Telegram, ошибка и повтор VKWebAppInit, один вызов Bridge при параллельной инициализации, получение launch data после ответа Bridge. Bridge/HTTP подменяются в тестах; настоящий VK iframe/WebView остаётся ручной проверкой. Telegram webhook пока без secret token. Профиль VK и код сообщений реализованы позднее; текущий статус указан в повторной сверке выше. Темы/платформенные действия остаются открытыми.
