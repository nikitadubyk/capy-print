# Уведомления клиентов и сотрудников VK — 9 октября 2026

Реализован сценарий, аналогичный текущим Telegram-уведомлениям: сообщение клиенту при переходе в `PRINTING`, `COMPLETED` или `CANCELLED`. `PENDING` и `PROCESSING`, сохранение комментария и повторное сохранение текущего статуса сообщений клиенту не создают. Новый заказ любой платформы отправляется сотрудникам в Telegram и настроенные диалоги VK.

## Дубликаты новых заказов сотрудникам

`POST /api/orders` сначала сохраняет заказ, затем вызывает общий `sendOrderNotification` из `lib/order-notifications.ts`. Telegram и каждый получатель VK начинают отправку независимо: сетевой сбой Telegram либо отказ одного VK-получателя не отменяет остальные попытки и не меняет HTTP 201 сохранённого заказа. Результат функции содержит отдельный статус Telegram и каждого `peerId`; очередь/журнал повторов пока не реализованы.

Добавлена серверная переменная `VK_ADMIN_PEER_IDS`: полные числовые ID получателей через запятую. Пример:

```dotenv
VK_ADMIN_PEER_IDS=123456789,987654321
```

Пробелы и пустые элементы игнорируются, повторяющиеся ID удаляются. Некорректное значение отключает VK-попытки с диагностикой `config` для этого поля, сохраняя отправку Telegram. Пустая переменная отключает дубликаты VK. Получатели задаются только на сервере; данные запроса заказа не могут их заменить. Используется существующий `VK_GROUP_TOKEN` того сообщества, чей inbox содержит диалоги.

В адресе `gimGROUP_ID/convo/PEER_ID` часть после `convo/` задаёт получателя. Для личного диалога это ID пользователя; для беседы — полный `peer_id`, уже включающий смещение `2000000000`. Отправляется `messages.send` с `peer_id`, без преобразования личного ID в ID беседы. Наличие аккаунта среди участников сообщества не гарантирует право писать ему: получатель должен разрешить сообщения сообщества, либо сообщество должно иметь доступ к беседе. VK применяет свои ограничения и может отказать в доставке. Контракт: [официальная схема messages.send](https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json).

Одна функция `formatOrderNotification` формирует номер, срочность, клиента/платформу/ID, профиль и переписку, параметры всех наборов, названия и ссылки всех файлов, комментарий, дедлайн и время создания. В Telegram сохранены HTML и экранирование; в VK передаётся обычный текст со всеми исходными данными и URL. `random_id` стабилен для нового заказа и конкретного получателя и использует отдельное пространство от уведомлений клиента о статусе. Отказ клиента от его личных уведомлений не отключает служебный список сотрудников.

В `lib/telegram.ts` добавлен таймаут 10 секунд и безопасная диагностика: HTTP status, разрешённый транспортный код (например, `ENOTFOUND`, `ECONNRESET`, `ECONNABORTED`), код ошибки Telegram API и классифицированная причина. Сырые ошибки, URL с bot token, payload заказа и произвольный `description` не логируются. Старое `status: undefined` само по себе не различало отсутствие HTTP-ответа и исключение до ответа сервиса. Сообщение UploadThing о callback подтверждает этап загрузки файла, а не доставку уведомления.

Проверки на заглушках: общий текст/URL для обеих платформ, разбор env и дубли ID, отправка всем получателям, зависший/недоступный Telegram, отказ одного VK peer, отсутствие конфигурации, неизменность сохранения заказа/HTTP 201 при сбоях всех каналов, защита получателей от клиентского ввода, стабильный `random_id`, отсутствие секретов в логах. 155 тестов без SQL-теста миграции, TypeScript, ESLint и production build прошли. Проверка HEAD к `api.telegram.org` без токена получила HTTP 302: домен был доступен из окружения проверки, но это не подтверждает доставку Bot API и не объясняет прошлый сетевой сбой. Настоящие сообщения не отправлялись, БД/Docker не использовались. Новых миграций для служебных получателей не требуется.

## Разрешение пользователя

После входа VK-пользователя общий layout один раз показывает диалог «Сообщения о заказе во ВКонтакте», если выбор ещё не сохранён. Есть два варианта: «Разрешить сообщения» и «Без сообщений». Крестик, Escape и закрытие нажатием снаружи отключены. Пока проверяется уже сохранённый выбор, диалог не показывается, чтобы не мелькать при каждом запуске. Telegram-пользователям он не показывается.

По кнопке разрешения вызывается `VKWebAppAllowMessagesFromGroup` с числовым ID сообщества. После подтверждения сервер проверяет разрешение VK и сохраняет выбор. В контракте SDK успешный ответ — `{ result: true }`, отказ/закрытие учитывается через Failed/rejected promise. Наш диалог при таком отказе остаётся открытым: пользователь может повторить разрешение или выбрать «Без сообщений». Обработка синтетического `result: false` — дополнительная защита в коде и тесте, не обещанный SDK способ отказа. Закрытие нативного диалога контролирует сам VK; ограничение закрытия применяется к диалогу приложения.

`GET /api/vk/messages/permission` требует действующую VK-сессию и берёт внешний ID пользователя из её identity. Ответ содержит `configured`, `groupId`, `allowed`, `enabled`; токен сообщества не попадает в клиент. `enabled: null` означает отсутствие выбора; `true` — согласие, `false` — отказ. Для сохранённого выбора GET не вызывает VK API. Ответы не кешируются HTTP-кешем.

`POST /api/vk/messages/permission` принимает только `{ enabled: boolean }`. Сервер сам определяет identity по сессии; согласие сохраняет только после проверки `messages.isMessagesFromGroupAllowed`. Отказ сохраняется без запросов к VK, в том числе при отсутствии настроек сообщества. При ошибке сохранения диалог остаётся открытым. Сервер отправляет сообщения только при сохранённом согласии и каждый раз дополнительно проверяет VK-разрешение, учитывая его отзыв.

Выбор хранится в `UserIdentity.vkMessagesEnabled`, поэтому действует после перезапуска и на другом устройстве. После отказа повторный автоматический запрос не показывается и сообщения не отправляются, даже если у сообщества осталось разрешение VK. Отдельный экран изменения выбора пока не реализован.

Подготовлена миграция [20261009000000_vk_messages_preference](../../prisma/migrations/20261009000000_vk_messages_preference/migration.sql): добавляет nullable Boolean, не удаляет и не меняет существующие данные. Prisma Client сгенерирован. Миграция не применена; до запуска нового кода её нужно применить на согласованном окружении вместе с ранее подготовленными миграциями сессий.

Это разрешение на **сообщения сообщества**, а не `VKWebAppAllowNotifications` для платформенных уведомлений приложения.

## Настройки владельца

### Восстановление после ошибки настроек — 9 октября 2026

Если GET возвращает `configured: false`, сервер не нашёл непустой `VK_GROUP_TOKEN` или корректный положительный числовой `VK_GROUP_ID`. Наличие обеих строк в env само по себе недостаточно. Из ссылки вида `wall-123456789_15` в `VK_GROUP_ID` нужно записать только `123456789`: без минуса, URL и номера записи после `_`. Во время исправления disabled-кнопки обнаружен именно формат `ID_номерЗаписи`; локальная строка `.env` исправлена без изменения токена и других переменных. Корректность токена и его права не проверялись через внешний VK API.

После изменения env перезапустите Next.js. Для приложения в Docker нужно пересоздать сервис `app` с актуальным `.env`; один restart существующего контейнера не обновляет его окружение. Если Next.js работает на компьютере, env читает этот процесс, а не контейнер PostgreSQL.

Диалог теперь предлагает «Проверить снова» и при отсутствии конфигурации. Пока выбор не сохранён, query считается устаревшей и обновляется при повторном mount/возврате фокуса либо вручную. Только сохранённое согласие/отказ кешируется без срока, поэтому повторного автоматического диалога после выбора нет. После POST отменяется предыдущий GET через AbortSignal: его поздний ответ не может вернуть `enabled: null` и открыть диалог снова.

Проверки: 6 тестов сообщений/query/маршрутов на заглушках без базы и сети; повторная проверка конфигурации, кеш сохранённого выбора и отмена запоздавшего GET. TypeScript, ESLint затронутых файлов, Prettier и production build прошли. В изолированном браузере с фактическим компонентом/hooks/Axios и заглушками HTTP/Bridge проверены disabled при `configured: false`, восстановление кнопки через «Проверить снова», согласие, закрытие диалога и reload без повторного вопроса; экран 320×640. Синтетический стенд не использовал реальные токены, БД, Docker и сообщения; после проверки удалён.

### Настройка сообщества

1. Выбрать сообщество, от которого будут приходить сообщения, и включить его сообщения в управлении сообществом.
2. Создать ключ доступа **этого сообщества** с правом `messages`. Сервисный ключ приложения и `VK_APP_SECRET` для этого не подходят.
3. На сервере заполнить `VK_GROUP_ID` (положительное числовое значение без минуса) и `VK_GROUP_TOKEN`. Шаблон: [env.example](../../env.example).
4. Перезапустить приложение после настройки окружения. Клиент получает публичный group ID через авторизованный endpoint; отдельный `NEXT_PUBLIC_*` не нужен.
5. В настоящем VK Mini App проверить согласие, отказ, отмену диалога, отзыв разрешения и сообщения при трёх статусах. Проверить web, Android и iOS. Ключ должен принадлежать тому же сообществу, что указано в `VK_GROUP_ID`.

Внешние настройки, токены, реальные сообщения и применение миграций в этой задаче не выполнялись. Callback API не требуется для проверки разрешения перед отправкой; настройка `message_allow`/`message_deny` и меню бота остаётся отдельным этапом.

## Отправка и границы надёжности

`lib/notifications.ts` формирует один текст статуса в двух представлениях: Telegram HTML и обычный VK-текст. Получатель VK выбирается по `UserIdentity.externalUserId`, а не внутреннему `User.id`. Для старых Telegram-аккаунтов сохранён fallback на `User.telegramId`.

`api/vk/server.ts` содержит серверный Axios transport с токеном сообщества в Authorization header. Адреса, версия `5.199` и таймаут находятся в `config/url.ts`, секретное окружение — в `config/vk-server.ts`. `lib/vk.ts` проверяет параметры и ответы, `lib/notifications.ts` выбирает отдельную функцию отправки VK или Telegram, её типы вынесены в `lib/types.ts`. Для `messages.send` передаются положительный `user_id` и `random_id`. Ошибки API могут приходить при HTTP 200 и обрабатываются отдельно. В логах нет Axios config, токенов или полных ответов VK.

Клиентские запросы находятся в `api/vk-messages/index.ts`, query/mutation options и ключи кеша — в `queries.ts`, React hooks — в `hooks.ts`. После сохранения выбора mutation обновляет только кеш текущего пользователя. Тексты диалога вынесены в `config/vk-messages.ts`.

PATCH сохраняет заказ до отправки. При конкурентных изменениях проверяет прежние `status` и `updatedAt`; проигравший запрос получает 409 и не отправляет сообщение. `random_id` стабилен для одного сохранённого перехода и меняется при новом переходе. Успешный API-ответ означает принятие сообщения VK, а не прочтение.

Ошибка или запрет сообщения не откатывают заказ. Пока нет сохранённого журнала доставки, очереди и ручного повторения в админке. При сбое после сохранения статуса сообщение может быть потеряно; повторное сохранение того же статуса намеренно не отправляет его снова. Это соответствует границам текущих Telegram-уведомлений. Для надёжного повторения нужен отдельный этап с событием доставки в транзакции и миграцией.

Проверка незакоммиченных изменений выявила также отсутствие гарантии порядка: при быстрых переходах PRINTING → COMPLETED проверка разрешения первого сообщения может задержаться, и «Заказ готов» придёт перед «Принят в работу». Это воспроизведено с полностью подменённым Axios, без сети и базы. `random_id` предотвращает дубли одного события, но не упорядочивает разные события. Нужна последовательная обработка событий одного заказа; результат доставки нужно сохранять и показывать сотруднику. Эти исправления пока не реализованы.

## Проверки без базы и Docker

Поведенческие проверки используют только подменённые Axios/Bridge и объект хранилища в памяти, без PostgreSQL, PostgreSQL WASM, Docker и сети:

```powershell
node --import tsx --test tests/auth/vk-messages.test.ts tests/auth/vk-notification-routes.test.ts tests/auth/notifications.test.ts tests/auth/mini-app-adapters.test.ts tests/auth/access.test.ts tests/auth/client-profile.test.ts tests/auth/vk-profile.test.ts tests/auth/order-list.test.ts
```

Покрыты согласие и отказ Bridge, неподдерживаемый метод, реальная серверная проверка через подменённый VK API, отзыв разрешения, защита endpoint от чужого ID и Telegram-сессии, незаданное окружение, некорректный ответ, VK API errors и сетевой сбой, выбор платформы, неизменность статуса при сбое доставки, повторный и конкурентный PATCH, стабильность `random_id` и отсутствие секретов в логах.

Нативный Bridge и реальная доставка требуют отдельной проверки после внешних настроек. Без неё интеграция не считается проверенной в VK.

После перехода к диалогу прошли 19 тестов с подменёнными API/хранилищем, TypeScript, ESLint и production build. Тесты расширены: сохранение согласия/отказа, повторный вход с сохранённым выбором, отказ без настроек VK, ошибка хранилища и запрет отправки до согласия. В изолированном браузере при viewport 320×640 проверены согласие через клавиатуру, отказ приложения и VK, повторный вход, запрет закрытия по Escape/снаружи, отсутствие настроек, ошибки API/Bridge/сохранения. База, SQL WASM, Docker, нативный VK и реальная доставка по указанию пользователя не запускались.

После выделения hooks/queries проверены все тесты кроме `migration.test.ts`: 137 прошли. Дополнительный тест проверяет отсутствие запроса до инициализации, обновление кеша после отказа, разделение по пользователю, повторный mount без нового GET и сохранение прежнего выбора при ошибке POST. TypeScript, ESLint изменённых файлов и сборка прошли. В браузере проверены фактические hooks/queries и Axios с временным backend/Bridge: согласие и отказ закрывают диалог, повторный вход не показывает его снова.
